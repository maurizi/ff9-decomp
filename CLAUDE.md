# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Matching decompilation of Final Fantasy IX (PS1, NTSC-U, 4 discs). Goal: C source that compiles to byte-identical binaries.

## Toolchain runs in Docker
- Everything except disc extraction and `make progress` runs in the container: `tools/docker.sh make verify` or `tools/docker.sh <cmd>`. The image (`tools/docker/Dockerfile`) rebuilds itself when the Dockerfile or `requirements.txt` changes. The host has no mips binutils.
- Submodules: `tools/maspsx`, `tools/m2c`, `tools/asm-differ`. Run `git submodule update --init` after cloning.

## Binaries
- 20 binaries, all rebuilt byte-identically by `make verify`: the boot exe (`src/main/`) and 19 code overlays from `FF9.IMG` dir 0 (`src/ovl_XX/`, XX = file id). Overlays are identical on all 4 discs. Format, load addresses and what each overlay probably is: `docs/ff9img.md` and `config/overlays.us.txt`. The overlays hold about 70% of the game code.
- Overlay yamls come from `tools/gen_ovl_configs.py`, which never overwrites an existing yaml (`--force` does). Hand edits stay, e.g. ovl_0b's `textbin` table and the per-source-file C subsegments (below). Overlays need `subalign: 4` and no section-end alignment, otherwise the build gains 0x10 of padding.
- Overlays at the same address overlap (six load at 0x800A7000), so their symbols mean nothing outside that overlay. Overlay-local declarations go in `include/ovl_XX.h` (which includes `ff9.h`), and `src/ovl_XX/*.c` includes that header.
- splat prints "Unable to determine a segment for … user-declared symbols" for every overlay because the main exe's symbol files are shared. It's harmless: overlay asm still uses the names (`DrawSync`, …).
- **Battle effect modules** (`fx_XXX`, XX = FF9.IMG dir 13 file id, `_N` = load group): 380 more binaries, the code chunks of the effect files, loaded at 0x801E7700 (some summon groups at 0x801EC700). Format: `docs/ff9img.md`; list: `docs/effect-modules.md` (`tools/effect_modules.py catalogue` writes it and `config/fxmods.us.txt`). `make extract-fxmod` (host, needs `extract-img`) writes `disks/us/fxmod/` and runs `tools/gen_fxmod_configs.py` (yamls and header/op symbols in `config/fxmod/`, never overwritten without `--force`). Make split/resplit/build/verify include them only when `disks/us/fxmod/` exists; verify prints one summary line. C lives in `src/fxmod/fx_XXX/fx_XXX.c` (one directory each, since all modules share addresses), declarations in `include/fxmod/fx_XXX.h`, which includes `include/btlfx_mod.h`.
- Modules call nothing directly: every call into ovl_0b goes through the export table, `BTLFX_EXPORTS(env)->name(...)` (`BtlfxExports` in `btlfx_mod.h`). Op handlers are `EffFn`s `(mode, work, env, Unk80100C78Entry *task, args)`. In the modules' view every export returns a value and takes word arguments (a call_value ties v0 to the function pointer; `btlfx_mod.h` explains), so `BtlfxExports` widens ovl_0b's void returns and s16/u8 parameters. They are game code from the same compiler (gcc 2.8.1 -O2 -G0). `ccprobe --bin fx_XXX` and `permute.py --bin fx_XXX` work as for overlays; `progress.py` lists them in a separate block (not in the game totals) and indexes their functions in `config/functions.fxmod.us.txt`.

## Decomp workflow
1. Pick a target: `make progress` shows per-binary totals. `python3 tools/progress.py --list [--bin ovl_0a] --min 40 --max 160 [--range 0x80026000-0x80030000]` lists remaining game functions.
2. Draft: `tools/docker.sh python3 tools/m2c/m2c.py asm/us/main/nonmatchings/main/<func>.s`. m2c guesses arguments from register use. A function that only touches `$a3` still takes 4 params, and `jalr` on `$a2` doesn't mean `$a2` is a parameter.
3. Batch-test in isolation: write several functions in a scratch file under `build/` (e.g. `build/batchN.c`) that only includes `ff9.h` (or `ovl_XX.h`), then run `tools/docker.sh python3 tools/ccprobe.py build/batchN.c --cc gcc-2.8.1-psx --aspsx 2.77 [--bin ovl_XX]`. A `*` means a byte match with relocations masked. A compile error prints `FAILED`, so don't read a missing score as a match.
4. Near misses: add `--show func_X` to ccprobe for our output next to the original. Typical fixes: param/return types (`andi`/`lbu` show u8, `sll`/`sra 16` show s16, `multu` shows unsigned), statement order, a temporary in a new local, and pointer-vs-index loops. Register-allocation-only differences go to the permuter: `tools/docker.sh python3 tools/permute.py <file.c> func_X --run -j 8` (results in `build/permuter/func_X/output-*/source.c`). Clean up its output before keeping it.
5. `python3 tools/integrate.py build/batchN.c [func ...] [--into src/ovl_XX]` moves function bodies over their `INCLUDE_ASM` lines, in whichever file of the binary's directory holds them (default `src/main`). Then `tools/docker.sh make verify` (under 1 s); only a sha1 `OK` counts.
6. In a built tree, `tools/docker.sh python3 tools/asm-differ/diff.py --no-pager -s <func>` also works. `-s` stops at `jr ra`.
- **Keep the README's progress current, but only when recording progress.** The commit that appends to `docs/progress.csv` (`make progress CSV=1`, "Record progress") also updates the README's Progress section from the same numbers: functions done/total, percentage of game code bytes, and how many of the 20 binaries are fully decompiled. Ordinary decomp commits leave the README alone, so parallel branches don't conflict on it.
- **All declarations live in headers** (`include/ff9.h` for game code, `include/psyq.h` for SDK types, macros and prototypes), so batch files and every source file share them. A main file's preamble is just `#include "ff9.h"` (an overlay file's: `#include "ovl_XX.h"`). Use `unkXX` field names (XX = hex offset) with pad arrays until the meaning is known, and prefer struct fields over byte-offset casts.
- `ccprobe` masks relocated fields, so a wrong struct offset or relocation addend can still score `*`. Treat it as a filter; only `make verify` proves a match.
- Jump tables: gcc emits `.align 3` for them, but the original objects were packed at 4 bytes, so the effect modules (and ccprobe/permute) rewrite it to `.align 2`. Every main/overlay binary is split per original source file (`TU_SPLIT` in the Makefile), and there gcc's own `.align 3` is kept, because each object's alignment reproduces the original padding. Switch functions that failed `verify` before this fix (e.g. ovl_15 `func_800A713C`) are worth retrying.
- Permuter on an overlay function: `tools/permute.py <file> <func> --bin ovl_XX --run -j 8`. It keeps `gte_*` macro calls unexpanded (late defines), since the permuter can't parse asm statements. `tools/docker.sh` runs containers with `--init`, so `timeout` really stops them; check `docker ps` for strays anyway.
- Checks for C that matches only because of MIPS register leftovers (they matter to ports, which compile src/ natively): `tools/void_returns.py` (void functions whose callers read $v0) and `tools/arg_check.py` (functions reading more argument registers than their C declares or their callers pass; `--why NAME --bin B` explains one). Both should report 0. Where passing the argument breaks the match, write `f(REG_PASSTHROUGH(x))` (`ff9.h`). A local pinned to a register (`register T v REG_ASM("$3")`, `ff9.h`) is the last resort when no C form reproduces the allocation (ovl_0a func_800C0038, func_800C07D8); ports define it empty. `tools/equiv.py docs/wip/<draft>.c` tests a non-matching draft against the original in a MIPS interpreter from random states.
- Square's code uses PsyQ macros such as `addPrim`/`setlen`, which compile to the bitfield mask sequences. It also inlines helpers: `func_80027F34` only matches by calling `static inline func_80027EDC_inline` (in `ff9.h`).

## Naming
- `docs/naming.md`: every name needs evidence, tagged in the symbols file (`[string]`, `[bios …]`, `[runtime]`, `[code]`). Header comments from the matching work are leads, not evidence. Rename with `tools/rename.py --from FILE --build` (no resplit needed). `make progress` shows naming progress.
- DuckStation + its MCP server (`mcp__duckstation__*`: memory, registers, breakpoints) is set up as described in `docs/emulator.md`.

## Compiler (verified empirically, not documented anywhere)
- Some original source files were built with **-O1** (e.g. ovl_0b 0x800C2DF4-0x800C8BE0: `$ra` is saved first and the prologue isn't scheduled; 0x800C7730-0x800C8BE0 inside it may use yet other flags). Give such a range its own splat C subsegment named `*_o1` (plus its own `.rodata` subsegment); the Makefile compiles `*_o1.c` with `-O1 -G0`. Probe with `ccprobe --flags "-O1 -G0"`.
- FF9 game code is **gcc 2.8.1** (`gcc-2.8.1-psx`, the Makefile default) with `-O2 -G0`, plus maspsx `--expand-div` (divides carry the ASPSX `break 7`/`break 6` guards). In `tools/probes/compiler_id_game.c`, 6 of 6 Square functions match only under 2.8.0 and 2.8.1; 2.7.2-cdk (FF8's main compiler) misses 3. 2.8.0 and 2.8.1 give identical output for everything except the event-script interpreter func_80039C38, which only matches under 2.8.1, so use 2.8.1 (`--cc gcc-2.8.1-psx` with ccprobe).
- `ASPSX_VERSION=2.77`: every version from 2.56 to 2.86 builds all 20 binaries identically, and below 2.50 they all fail.
- PsyQ library code was built by Sony with a different toolchain (e.g. `CdInit` stores globals via `lui $at`), so don't use library functions to test compiler hypotheses.

## Library code
- 229 PsyQ functions in the main exe were identified by signature (`tools/psyq_match.py [--bin PATH:VRAM:TEXT_START:TEXT_END]`, using lab313ru/psx_psyq_signatures cloned outside the repo) and listed in `config/symbols.psyq.us.txt`. Overlays contain essentially no library code; the exception is ovl_64 (FMV player) with libpress, in `config/symbols.psyq.ovl_64.us.txt`. Single 32-byte signature hits are noise. They match libs from PsyQ 4.1–4.7. They are **interleaved** with game code (dense at 0x80012000–0x80024000), not just at the end of `.text`. Don't decompile them; `progress.py` excludes them.
- Unnamed functions next to library clusters may be unsigned library code (e.g. libds). Check what calls them before investing in one.

## Splitting
- Every binary is split into one C subsegment per recovered original source file (single-TU overlays keep `ovl_XX.c`; offset 0 of each overlay's rodata, the overlay id, is its own object) (`docs/source-files.md`: boundaries from library placement, hand-written asm modules, jump-table alignment mod 8, rodata ownership, data order). Each C subsegment has its paired `.rodata` subsegment, so jump tables migrate into the function files; unpaired rodata fails to link on `.L` labels. Files without an evidence-backed name are `tu_<address>.c`; PsyQ runs are `psyq_*.c`, hand-written asm `*_asm.c`. Resplit gives new files the binary's `#include` lines (and a file taking over a removed file's first item inherits its preamble). Main's yaml uses `subalign: 4` and no end alignment, like the overlays.
- splat **never rewrites an existing `.c` file**. After adding symbols or changing a yaml, run `tools/docker.sh make resplit` (`tools/resplit.py`): it re-splits every binary and merges each file's preamble and hand-written bodies back in, even when a function moves to a different file. If it reports missing slots it keeps `*.bak` files and refuses to run again until they're resolved; merge by hand, then delete them. Never delete a `.c` file to regenerate it. Commit before risky resplits.
- Only run `make resplit` after a config or symbol change, never after a plain merge (the asm only depends on configs). Text between items (multi-line comments, `#define`s, top-level `__asm__` padding) travels with the item below it, `INCLUDE_RODATA` lines keep their hand-placed position, and a body defined as `f_def` with an `__asm__("f")` label fills `f`'s slot, so an unchanged layout round-trips byte for byte. Check `git diff src` after every resplit anyway. `progress.py --write-index` refuses when asm/ comes from a plain split.
- `make clean` or deleting `build/` also removes splat's linker scripts (`build/us/*.ld`), so run `make resplit` before building again.
- `make progress` reads every function from the committed index `config/functions.us.txt`. A plain `make split` only writes asm for functions still `INCLUDE_ASM`'d. After any config change that moves function boundaries, run a full `make resplit` (restore `src/` from git if it mangles anything) and then `python3 tools/progress.py --write-index`.
- Symbols go in `config/symbols.us.txt` (`name = 0xADDR; // type:func`), then `make resplit`. Renaming a decompiled function also needs its C definition renamed.
- splat applies `config/symbols.us.txt` to every overlay's split too, so never put an overlay address there: when main calls an overlay function, name it in `config/xrefs.us.txt` (linker-only, main's link) and in the owning overlay's symbols file. An overlay calling another overlay (e.g. ovl_64) gets a line in its own `symbols.ovl_XX.us.txt`. `tools/rename.py` only renames inside the owning binary, so check other binaries for the old name after every rename.

## Runtime investigation (emulator)
- `tools/emu.py` (host-side, not Docker) drives PCSX-Redux running FF9: trace calls to a function, watch who writes a global, diff RAM across a button press, take screenshots, and use save states (field, menu and battle states already exist). Setup and workflow: `docs/emulator.md`.
- Investigations record evidence and proposed names in `docs/runtime-findings.md`. Applying the names (symbols file, `make resplit`, `make verify`) and marking entries **applied** is the decomp side's job. Only one investigation runs at a time, since there's a single shared emulator.

## Game data — never commit
- Disc images (raw 2352-byte CloneCD `.img`) are in `disks/us/raw/`. The extracted exe is `disks/us/SLUS_012.51`, `FF9.IMG` is in `disks/us/discN/` (`make extract-img`), and the code overlays are in `disks/us/ovl/XX.bin` (`make extract-ovl`). Never commit `disks/`, `asm/`, `build/` or `assets/`.
- Don't copy game data into C either. Text banks and other blobs stay `INCLUDE_RODATA` (give the symbol `// force_not_migration:True` in the symbols file so splat emits its `.s` even after the function that uses it is decompiled). Short debug/printf strings and small numeric tables that functions need to match are fine in C.

## Layout facts
- Boot exe `SLUS_012.51` (sha1 `e37e8c4d…1764`) is **byte-identical** on all 4 discs, as are the code overlays. Per-disc differences are data in other `FF9.IMG` directories.
- Exe: vram `0x80010000`, entry `__SN_ENTRY_POINT` `0x80012B68`, gp=0. `.rodata` 0x800 → `.text` 0x2FA0 → `.data` 0x56DE0–end.
- `g_gameState` (0x8006794C) is the main game-state pointer (`GameState` in `include/ff9.h`); `->unk1C` points to a large `GameData` block.
